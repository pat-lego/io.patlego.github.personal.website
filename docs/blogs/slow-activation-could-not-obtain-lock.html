Present but not available: slow OSGi activation and "Could not obtain lock"

The OSGi console says everything is fine. Bundle active. Service registered. Every reference satisfied. And yet your component is not active, or getService() just handed you null. The only clue is one line in the log:

FrameworkEvent ERROR (org.osgi.framework.ServiceException: Service factory exception: Could not obtain lock)

Short version: in Apache Felix SCR (the Declarative Services runtime behind Felix and Sling based containers), a component that is present is not necessarily available. If its activate() is slow, everyone else who asks for it during that time waits on a lock, and that lock has a timeout. When it expires, they leave with nothing, even though the service would have been ready a few seconds later.

This is not new. It has its own Felix ticket, FELIX-6048, open since 2019. What is missing is a plain explanation of what the message means, so here is one, with a sample you can run: pat-lego/scr-lock-contention-sample.

Registered is not the same as ready

A component that provides a service is delayed by default. Once its references are satisfied, SCR registers the service, but it does not create the object yet. The instance is built, and activate() runs, the first time someone calls getService(). It is a restaurant that is "open" while the chef is still driving to work.

While activate() runs, SCR holds that component's state lock. Anyone else who needs the component waits for the lock, but not forever (AbstractComponentManager.java):

if (!lock.tryLock(getLockTimeout(), TimeUnit.MILLISECONDS)) { dumpThreads(); throw new IllegalStateException("Could not obtain lock"); }

The timeout is ds.lock.timeout.milliseconds, default 5000 ms (ScrConfiguration.java). Five seconds. That is the whole patience budget. Because SCR registers the service as a ServiceFactory, the framework wraps the exception in a ServiceException, logs it as a FrameworkEvent ERROR, and the caller gets null (ServiceRegistrationImpl.java).

Reproducing it: one slow component, two callers

The sample has a component whose only hobby is being slow:

@Component(service = SlowActivationService.class) // delayed by default public class SlowActivationServiceImpl implements SlowActivationService { @Activate protected void activate(final Config config) { // stands in for network calls, cache warm-up, big files... Thread.sleep(config.activation_delay_ms()); // 15000 ms } }

Then two threads ask for it, one second apart, from two different bundles. The first one (the holder) triggers activation and sits inside activate() holding the lock. The second one (the waiter) waits five seconds and gives up:

09:41:11.799 [holder] activate() START; sleeping 15000 ms 09:41:12.803 [waiter] getService() START 09:41:17.878 [waiter] getService() returned null after 5075 ms 09:41:17.879 FrameworkEvent ERROR (... Service factory exception: Could not obtain lock) 09:41:26.804 [holder] activate() END after 15005 ms

At 09:41:17 the service is registered and nine seconds away from working perfectly, and the waiter is told there is nothing there. Nothing is broken. It is just timing.

Why two bundles? With two threads from the same bundle, the Felix framework makes the second one wait on its own latch before it ever reaches the SCR lock (ServiceRegistry.java), so it never times out. In a real system a popular service has many consumer bundles, so this is the normal case, not a lab trick.

The real damage: components that reference it

Most code does not call getService() by hand. It uses @Reference:

@Component(immediate = true) public class ReportGenerator { @Reference // mandatory, static private SlowActivationService slowService; }

To activate ReportGenerator, SCR first collects its references by calling getService() on each one (collectDependencies()). If the slow service is mid-activation for another bundle, that call times out, SCR logs Could not obtain all required dependencies, getService returning null (SingleComponentManager.java), and ReportGenerator is not activated. Its own activate() never runs, so your code logs nothing at all.

  • The component shows as satisfied but not active. The dependency is right there. It just was not available at the moment SCR asked.
  • For a mandatory reference there is no automatic retry. SCR's late-binding path only covers optional references (cardinalitySatisfied(0) in DependencyManager.java). An immediate component stays down until something triggers a new attempt: a config change, the service being re-registered, or a restart.
  • A delayed consumer is retried the next time someone asks for it, so there the symptom is intermittent.

That is why it mostly shows up at startup or right after a deployment, when everything activates at once. And why "have you tried restarting it?" works so often: it rolls the dice on timing again.

You are not the first to hit this

FELIX-6048 was opened in 2019 against SCR 2.1.14 ("w/o having ever seen any impact"). Since then it has collected reports from 2.1.20, 2.2.2 and 2.2.4, comments like "no workaround except restarting the whole thing", and requests from the maintainers for a test case and a debug thread dump. No reproducer was posted, and it is still open. Older tickets with the same message (FELIX-3645, FELIX-3862) were real SCR bugs and were fixed. The timeout stayed, by design.

Other projects have hit it too, and the ones that dug in found the same thing:

  • Enonic XP #8173: repository setup inside activate() was slow on a slow disk. The maintainers called raising the timeout "not very robust" and moved toward async initialization.
  • openHAB #2779: a constructor that installed add-ons "takes some time", and the service was injected into others before it finished.
  • A FELIX-6048 comment from OpenDaylight: "the component is being accessed via Service Registry while its activate() method is still executing", with timestamps that match the sample almost exactly.
  • ONOS / Atomix #1055 and OpenIDM #228: the same prebind → collectDependencies stack at startup.

Every report has the stack trace and "a restart fixed it". Few say what it means: some component held its lock longer than the timeout, usually because its activation was slow, and whoever needed it gave up. The stack tells you which side you are on. Through prebind → collectDependencies: a dependent component failed to collect a reference. Straight from your own getService(): a direct lookup got null. The same timeout also guards reconfiguration and deactivation, which is why those stacks show up too. Either way, go find the thread holding the lock.

Getting SCR to show you who holds the lock

That dumpThreads() call writes a full thread dump at the moment of the timeout, but only when the component's logger is at DEBUG (source). The logger name is the component's implementation class, not only org.apache.felix.scr. Two gates must both be at DEBUG:

  • OSGi Log Admin, which decides whether SCR builds the dump at all. In the sample: org.osgi.service.log.admin.cfg.json.
  • Your logging backend, so the entry reaches the log file. In the sample: the Sling logger config.
// org.osgi.service.log.admin.cfg.json { "<fully.qualified.ImplementationClass>": "DEBUG" }

The dump is taken by the thread that gave up, and it does not name the lock owner (LockOwnerId is -1 everywhere, which is about as helpful as it sounds). Find the holder by its stack instead: the thread inside getServiceInternal → createComponent for the same component. The frames above that are your slow code.

name: scr-lock-test-holder State: TIMED_WAITING ...SlowActivationServiceImpl.activate(SlowActivationServiceImpl.java:52) ...SingleComponentManager.createComponent(SingleComponentManager.java:115) ...SingleComponentManager.getServiceInternal(SingleComponentManager.java:974)

How to avoid it

Keep activate() boring. Read config, assign fields, return. Network calls, cache warm-up and big file parsing do not belong inside SCR's lock.

Do the slow part somewhere else. Kick it off on your own executor and let callers wait with their own timeout, or initialize lazily on first use:

@Activate protected void activate(final Config config) { executor = Executors.newSingleThreadExecutor(); // returns immediately, SCR releases the lock right away client = CompletableFuture.supplyAsync(() -> Client.connect(config), executor); } public Result doWork() throws Exception { return client.get(2, TimeUnit.SECONDS).call(); // caller picks the timeout } @Deactivate protected void deactivate() { executor.shutdownNow(); }

Do not just raise the timeout. ds.lock.timeout.milliseconds is framework-wide. Raising it does not make anything faster. It makes everyone wait longer for anything that is stuck, and hides the slow activate().

immediate = true helps a little. It moves activation to startup instead of the first request, which can shrink the window. The lock is still held for the full activate(), so it does not close it.

Know the smell. Satisfied but not active, and its activate() never logged a thing? Search for Could not obtain lock and Could not obtain all required dependencies around startup.

Try it yourself

The sample project fails the same way on every run, which is exactly the kind of reproducer FELIX-6048 asked for. It includes the slow component, the two-bundle runner, a servlet to trigger another run, the logging config, and a script that formats SCR's one-line thread dump. Install it on a local Sling-based author instance, then:

mvn clean install -PautoInstallSinglePackage curl -u admin:<password> -X POST -H "Referer: http://localhost:4502" \ http://localhost:4502/bin/scrlockdump/run grep -n -E "scr-lock-test|Could not obtain lock|: Thread dump" \ crx-quickstart/logs/error.log python3 tools/format_scr_threaddump.py crx-quickstart/logs/error.log

The takeaway: in Declarative Services, "registered" means "can be activated", not "is ready". A slow activate() turns every concurrent consumer into a five-second race, and the losers get null from a service that is right there.
