Java makes it easy to write bad code

Let me be clear up front: I am not saying Java is slow. I've spent the last decade in the JVM and I'll defend its performance all day. What I've spent the last few months relearning, over and over, across different codebases, is something different — Java makes it dangerously easy for a developer to write code that runs correctly and is simple to write, while quietly guaranteeing bad runtime behavior the moment it meets production traffic. None of these are exotic bugs. They're one line each. That's exactly the problem.

All three examples below share the same shape: a servlet container hands you a fixed, finite pool of request-handling threads. Every one of these mistakes converts that pool from "finite but self-recovering" into "finite and slowly strangled." Let's go through them.

1. synchronized turns your parallel container sequential

synchronized is one keyword. It costs nothing to type on a method signature, and it does exactly what it says — it stops more than one thread from executing that method at a time. To be fair to Java here: that's not a design flaw, that's the feature working as intended. The problem isn't that synchronized exists, it's how easy it is to reach for it at the wrong granularity. A servlet container like Tomcat or Jetty runs with a fixed thread pool — say 200 threads — specifically so that 200 requests can make progress at the same time. The moment you slap synchronized on a method that does I/O, a network call, or anything slower than a few CPU cycles, you've turned a resource meant to serve 200 concurrent requests into a resource that serves one request at a time while 199 others queue up on the monitor.

// Looks harmless. It's a single, well-intentioned cache guard. public synchronized ProductData getProduct(String sku) { ProductData cached = cache.get(sku); if (cached != null) { return cached; } // Network call to a backend service, held INSIDE the lock. // Every other request thread now queues behind this one call. ProductData fresh = backendClient.fetchProduct(sku); cache.put(sku, fresh); return fresh; }

Under low traffic this never shows up in testing. Under real traffic, with a fixed pool, every thread that hits this method funnels through a single lock while one of them is off making a network call. You didn't write a bug. You wrote a bottleneck, and it compiles clean and passes every unit test you'll write for it.

Here's what that actually looks like on a real box. This ran behind a Tomcat connector with a 200-thread pool. p99 latency on /product/{sku} was sitting around 40ms for weeks. Then the backend catalog service had a routine slowdown — nothing dramatic, just its own p99 going from 80ms to 4 seconds during a reindex. A thread dump taken during that window looked like this:

Notice these are two different mechanisms, not one. exec-9 is RUNNABLE — it's actually doing work, just slow work, stuck reading bytes off a socket inside Apache HttpClient. The other 196 never even get that far: they're BLOCKED (on object monitor), sitting at the exact entry point of getProduct(), because that's the only place the JVM will let them wait when the monitor is already held. They aren't slow. They aren't doing I/O. They're not doing anything at all — that's what "blocked on entry" means. 197 of 200 request threads either doing one slow network call or stuck queued behind it, on a servlet that has nothing to do with the reindex — they just happened to ask for a SKU that wasn't warm in the cache while exec-9 held the lock. p99 across the entire application, not just this endpoint, went from 40ms to just under 30 seconds inside four minutes, because the acceptor queue backed up behind those 200 exhausted threads and every other endpoint started queueing behind them too. Nobody touched a deploy. The only thing that changed was one downstream dependency getting slower for a few minutes.

And before anyone assumes this is only a rookie mistake — it isn't, and it's old enough to predate most of us. java.util.Vector and java.util.Hashtable synchronize every single method — get, put, size, elementAt, all of it — on the instance. It's still true today, in the current JDK, for backward compatibility. The JDK's own Javadoc for Vector tells you outright: "If a thread-safe implementation is not needed, it is recommended to use ArrayList in place of Vector." That warning exists because enough people shared a Vector or Hashtable across worker threads and turned every access — including plain, harmless reads like checking the size — into traffic serialized through one lock. The language shipped the unsafe-by-default replacements (ArrayList, HashMap) specifically because this exact mistake was common enough to need a documented workaround.

Go look at the source today and it's still there, unchanged, in Vector.java:

// From the OpenJDK source, java.util.Vector public synchronized Iterator<E> iterator() { return new Itr(); }

Read that again: iterator() does nothing but allocate a small object. There's no I/O, no computation, nothing that takes measurable time on its own. And it's still synchronized on the whole Vector, because every method is, unconditionally, whether it needs to be or not. Share one Vector across worker threads and even something as innocuous as iterating it repeatedly serializes those threads against each other. That's the real lesson: the JDK's own authors didn't synchronize surgically either — they synchronized the entire class, and later had to ship an entirely separate, unsynchronized collection API to undo it.

2. Collections have no bound, and nothing stops you from filling them

To push back on my own framing slightly: ArrayList does have a default initial capacity (10), and it resizes itself as you add to it, so "no default size" isn't quite the precise problem. The real problem is that there's no cap, and Java gives you zero friction between "read a result set" and "hold the entire result set in memory, per request." Nothing in the language nudges you toward streaming, pagination, or bounded batching. It's genuinely easier to write the unbounded version.

// Easiest possible way to write this. Also the most dangerous. public List<OrderRecord> getAllOrders(String accountId) { List<OrderRecord> orders = new ArrayList<>(); ResultSet rs = statement.executeQuery( "SELECT * FROM orders WHERE account_id = '" + accountId + "'"); while (rs.next()) { // Every row becomes a live object, held for the life of the request. orders.add(mapRow(rs)); } return orders; // Could be 12 rows. Could be 4 million. }

This is worse specifically because it's per-request. A memory leak that grows slowly over the life of an application is bad but at least visible in monitoring over time. A list like this lives and dies with a single HTTP request — so under a burst of concurrent requests against a large account, you can spike the heap in seconds, not hours, and the garbage collector can't reclaim memory that's still reachable from an in-flight thread stack. GC was never going to save you here; it was only ever going to buy you a slightly later OutOfMemoryError.

Concretely: one account had accumulated 2.3 million orders over a few years — nothing unusual for a long-lived customer. Each mapped OrderRecord retained around 440 bytes once you factor in the object header, its String fields, and their backing char[] arrays. That's roughly 1GB for one call to getAllOrders. On its own that's survivable. The problem was a nightly reconciliation job that fanned out and called this same endpoint for twelve large accounts concurrently. A 16GB heap doesn't have twelve spare gigabytes lying around next to everything else already resident. Here's the tail end of the GC log before it went down:

3. HttpClient has no default timeout, so a slow backend becomes your outage

This is the one I won't soften at all. java.net.http.HttpClient does not set a connect timeout unless you call .connectTimeout(...) on the builder, and it does not set a request timeout unless you call .timeout(...) on the individual request. Skip both — which is exactly what the five-line "quick and dirty" example everyone copies from Stack Overflow does — and a single unresponsive downstream service can hold that connection, and the thread that's blocked on it, open indefinitely.

// Compiles. Works in the demo. No timeout anywhere. HttpClient client = HttpClient.newHttpClient(); HttpRequest request = HttpRequest.newBuilder() .uri(URI.create("https://downstream-service.internal/api/data")) .build(); // If downstream never responds, this thread never comes back. HttpResponse<String> response = client.send(request, HttpResponse.BodyHandlers.ofString());

Now put that inside a servlet handler running on a fixed thread pool. Every request thread that happens to call this slow, timeout-less client during a downstream blip parks itself, waiting forever for bytes that may never come. You don't need the downstream service to go fully down — just slow and half-hanging is enough. One at a time, your thread pool fills with threads stuck on sockets, and requests that have nothing to do with that backend start queueing behind requests that do. That's thread starvation, and it's caused entirely by an object you constructed with sane-looking defaults that were never actually safe defaults.

This exact shape took down a checkout service I supported. A third-party fraud-scoring API started accepting TCP connections and then just... not responding — no RST, no FIN, no error, just silence after the TLS handshake. Over about six minutes, every request thread that happened to touch fraud scoring got stuck on the same read. A thread dump at minute five looked like this:

Why your test suite will never catch any of this

All three of these shipped with green builds and full test coverage. That's the part worth sitting with. Unit tests mock the backend client, so it returns in microseconds and the lock is never held long enough to matter. Test fixtures have a dozen rows in them, not 2.3 million, so the ArrayList never grows past a few kilobytes. Integration tests hit a fraud-scoring stub that always responds, so the missing timeout is never on the critical path. None of these tools are wrong to use — mocks and small fixtures are exactly what make tests fast and deterministic. But that's precisely why they can't see the failure mode: the bug isn't in the logic, it's in what happens when that logic meets concurrency and scale that a single-threaded test running against a stub will never produce. A code reviewer reading these diffs in isolation, one file at a time, has the same blind spot a unit test has. You need production traffic, a real account size, or a genuinely slow dependency to see any of this — which is exactly why it tends to show up for the first time in an incident channel instead of a pull request.

The pattern underneath all three

None of these are Java "bugs" in the sense of broken behavior — synchronized synchronizes, lists grow, and HttpClient sends the request you asked it to send. Each one does exactly what its contract says. The problem is that the contract's defaults and the easiest, most obvious way to use the API are tuned for correctness and simplicity in isolation, not for behavior under a fixed, shared thread pool serving concurrent traffic. Python, Node, Go — they all have their own versions of this trap. But servlet containers specifically hand you a fixed budget of threads and expect you to spend it wisely, and Java's standard library will happily let you write the one-liner that spends it badly. That's the theme for this post: not "Java is slow," but "here's how easy it was for someone to make it slow."

What actually fixes each of these

None of these fixes are clever. They're all slightly more work than the version that caused the problem, which is exactly why the problem version keeps getting written.

Unbounded lists: paginate. Don't return getAllOrders(). Return a page, with a cursor or offset, and make the caller ask for the next one. It's more code on both sides of the call — you now have to think about page size, sort stability, maybe a total count — and it's worth it, because the alternative is a request handler whose memory footprint is defined by the customer's data volume instead of by you.

Missing timeouts: set one, and have a fallback. Every outbound call gets an explicit timeout, full stop — connect timeout and request timeout, both set, on every HttpClient call you write. And when that timeout fires, don't just propagate a 500 — decide what degraded-but-alive looks like for that endpoint. Serve cached or default content, return a partial result, whatever fits. It's harder to write than "just call it and return what comes back," but a slow dependency should degrade your response, not take one of your threads hostage indefinitely.

synchronized: avoid it, don't just use it carefully. This one I'll say plainly rather than hedge: in my opinion, if you find yourself reaching for synchronized in request-handling code, that's a sign the design is wrong, not a sign you need a more careful lock. Reach for a ConcurrentHashMap, an AtomicReference, an immutable snapshot you swap out, a proper cache library with its own bounded concurrency — anything that doesn't hand a shared mutex to code running on a fixed thread pool. It's a stronger stance than "use it sparingly," but I've yet to see a servlet-container synchronized block that couldn't have been a better-designed data structure instead.
